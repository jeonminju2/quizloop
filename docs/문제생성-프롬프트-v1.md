# 문제 생성 프롬프트 v1 설계

실제 코드: `backend/app/prompts/question_generation_v1.py`. 여기는 왜 이렇게 설계했는지 정리.

## 1. 설계 목표

1. **환각 방지**: 업로드 자료(RAG로 뽑은 chunk)에 없는 내용을 문제로 만들지 못하게 한다.
2. **출력 안정성**: 매번 파싱 가능한 고정 JSON 구조로 나오게 한다 (마크다운/설명 텍스트 섞이는 것 방지).
3. **추적 가능성**: 모든 문제가 어떤 개념(concept_id), 어떤 근거(chunk_id)에서 나왔는지 남긴다 — DB스키마의 `questions.source_chunk_id`와 연결.
4. **오답 분석과의 연결**: 객관식 오답 보기를 "그럴듯하지만 틀린" 것으로 만들되, 다른 개념과 헷갈릴 만한 오답을 최소 1개 포함시켜서 이후 `concept_confusion` 태깅이 실제로 의미 있게 작동하도록 한다.
5. **재출제 대응**: 최초 출제(v1)와 취약개념 기반 재출제(v1.1 variant)를 같은 스키마로 처리하되, 프롬프트 지시만 다르게 준다.

## 2. 구조화 출력 방식 — tool_choice 강제

일반적으로 "JSON으로 출력해줘"라고 프롬프트에 쓰면 가끔 마크다운 코드블록이 섞이거나 설명이 붙는 문제가 있다. 그래서 Anthropic API의 tool use를 **강제(`tool_choice: {"type": "tool", "name": "submit_questions"}`)**해서 모델이 무조건 정의된 스키마로만 응답하게 만들었다. `services/llm_client.py`의 `call_with_tool_schema()`가 이 부분을 담당하고, 실패 시 1회 재시도한다.

이 방식의 장점: 프론트/DB 저장 코드에서 예외 처리를 최소화할 수 있고, "이 프로젝트는 LLM 응답을 프로덕션에서 안정적으로 다루도록 설계했다"는 포트폴리오 포인트로 바로 연결된다.

## 3. 시스템 프롬프트 핵심 규칙 (7개)

`SYSTEM_PROMPT` 상수 참고. 요약하면:

1. 근거 자료 밖 내용 금지 (환각 방지)
2. 문제-개념-청크 3자 연결 강제
3. 스키마 외 텍스트 금지
4. 오답 보기에 "헷갈릴 만한 오답" 최소 1개 포함
5. 난이도 3단계 기준 명시 (easy/medium/hard — 무엇을 묻는지 구체적으로 정의)
6. 단답형은 채점 가능한 형태로 제한
7. 재출제 시 이전 문제와 표현을 다르게 (반복 방지)

## 4. 유저 프롬프트 조립 — 두 가지 버전

### (1) `build_user_prompt()` — 최초 출제

입력: 자료명, 대상 개념 목록(id+이름+설명), 근거 청크(id+내용+페이지번호), 문제 수, 난이도, 문제 유형.

구조: `[자료명] → [대상 개념 목록] → [근거 자료] → [출제 요청]` 순서로 블록을 나눠서 모델이 각 섹션의 역할을 명확히 구분하게 했다.

### (2) `build_regeneration_user_prompt()` — 취약개념 재출제 (v1.1 variant)

최초 출제와 다른 점:
- `[대상 개념 목록]` 대신 `[취약 개념 목록]`을 주되, 각 개념 옆에 **최근 오답 횟수**를 같이 표시해서 "오답이 많을수록 더 많이/다양하게 출제하라"는 지시와 연결.
- `[이전에 출제된 문제]` 섹션을 추가해서 동일 문장 반복을 방지 (`weak_concept_stats`, `source_quiz_set_id` 기반으로 이전 문제들을 가져와 전달).

두 함수 모두 같은 `QUESTION_GENERATION_TOOL_SCHEMA`를 쓰기 때문에, 저장/검증 로직(`_persist_questions`)은 하나로 공유된다 — 최초 출제든 재출제든 동일한 파이프라인을 탄다.

## 5. 출력 스키마 요약

```json
{
  "questions": [
    {
      "type": "multiple_choice | short_answer",
      "concept": "문제가 검증하는 개념명 (입력으로 준 개념 목록 중 하나여야 함)",
      "question_text": "...",
      "options": [{"text": "...", "is_correct": true|false}, ...],
      "correct_answer": "...",
      "explanation": "...",
      "source_chunk_id": "입력으로 준 chunk_id 중 하나"
    }
  ]
}
```

## 6. 알려진 한계 (v1 시점)

- `concept` 필드가 모델이 만들어낸 문자열이라, 입력 개념 목록에 없는 이름을 낼 가능성이 있음 → 현재는 `_persist_questions`에서 매칭 안 되면 조용히 스킵. **개선 필요**: 스키마에 `enum`으로 개념 이름을 강제하거나, 실패 시 재시도 로직 추가.
- `source_chunk_id`가 실제 전달한 chunk 목록에 있는지 검증하는 로직이 아직 없음 (신뢰 기반). **개선 필요**: 저장 전에 chunk_id 존재 검증 후 없으면 재시도.
- 단답형 채점이 정확매치라 표현이 다르면 오채점 가능 (`grading.py`에 TODO 표시함). 구조화 출력과는 별개 이슈지만 v1 문제 생성 시 "채점 가능한 답만 내라"는 규칙(6번)으로 최대한 완화.

## 7. 다음 버전(v2) 후보

- Few-shot 예시 1~2개를 시스템 프롬프트에 추가해서 난이도 기준을 더 일관되게
- `concept` 필드를 자유 텍스트 대신 개념 id의 enum으로 제한
- 생성 후 자체 검증 단계(self-check) 추가: "이 문제가 근거 자료로 풀 수 있는가?"를 모델에게 한 번 더 확인시키는 2-pass 구조
